# 诊断基线协议

## 执行前门槛（本轮未执行）

1. 规格静态校验通过。
2. 判分器契约测试通过；当前只写好了测试，尚未运行。
3. 适配器实现并验证隔离、重置、完整账本、异常/取消和状态快照。
4. 所有场景都能明确归类 executed、blocked、not_run，不支持的故障不能伪造。
5. 模型实验需另行明确模型、配置、预算与凭证来源；默认无付费调用。

## 建议的首轮执行顺序

1. mock_rules：固定数据和无模型的当前规则路径，先排除可重复工程问题。
2. mock_model：同一固定业务世界，真实模型参与；记录模型与Prompt版本、温度、用量和重复次数。
3. lab_rules / lab_model：独立实验服务联调，另外采集权威业务事实；不得复用合成fixture判分。

第一轮诊断不要求全通过，不在同一轮中修改业务代码。先冻结输出，再分类和选修复项。

## 重复、划分与防止过拟合

- 规则模式先确认单次可重复；模型模式后续可从每场景3次起步，预算允许再增加。3次只是小样本，不能宣称稳定统计结论。
- 当前发展集24、保留集6，全部位于本地可见文件中。它们是流程上的分组，不是保密测试。
- 调优主要使用发展集，保留集在版本候选确定后再检查。需要更可信泛化证据时，另行编写未参与开发的新任务。
- 开发者/调优Agent可见测试规格，部署中的任务Agent不可接收判据或标准答案。

## 结果报告

- 分别列出pass/fail/needs_review/not_evaluable/blocked/not_run/deferred数量。
- 同时报告已判定通过率与判定覆盖率；少量已完成场景不能冒充全量通过。
- 规则、模型、真实服务模式分别报告，不合并成一个成功率。
- 按单站、多轮、多站、故障、动作、权限分组展示错误。
- 价格/预算/越权/重复写入等阻断性违规单独列出，不能被文案质量平均分抵消。
- 用量缺失记为未知，不记为0；成本只有在模型计价与用量来源明确时计算。
- 延迟需覆盖完整多轮任务，另外给每轮和阶段耗时。失败/超时和成功样本分别说明，不只挑快的成功结果。
- 保存代码版本、未提交改动哈希、规格/fixture版本、适配器版本、模型/Prompt配置、运行环境。

## 失败分类

解析/条件合并 → 参数映射 → 上游业务/协议 → 候选补查 → 硬条件校验 → 状态与幂等 → 展示解释 → 证据采集不足。

原因必须由证据支持，例如“返回180”不直接证明Java有错，需要依次核对计划、实际HTTP参数、Java绑定值与查询结果。

## 下一轮优化

选择一个失败簇，先写原因假设与改动范围，修改后比较同一批任务。独立判分标准不跟着修复随意放宽；标准确有错误时升级规格版本，旧结果不直接混比。

RAG和记忆新模块先完成自己的规格与测试，再接实验Agent做原有场景回归。功能未实现时保持deferred，不能计入当前通过率。
